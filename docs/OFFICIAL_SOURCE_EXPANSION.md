# 官方源扩展记录（2026-10-15）

本轮把「官方源抓得太浅」这个瓶颈定位并解决。结论先行：**最大的官方活动源被读了 1.8%，不是没有源，是读得不够深。**

## 一、问题定位过程

### 先测「政府站能不能提供未来活动」

对苏州市文广旅局和市政府站的各个栏目做了可见文字与未来日期的统计：

| 栏目 | 可见文字 | 页面上的未来日期 |
| --- | ---: | ---: |
| 文广旅局 活动信息 第1页 | 1,287 | **0** |
| 文广旅局 活动信息 第2页 | 3,038 | **0** |
| 文广旅局 文旅要闻 | 1,247 | **0** |
| 文广旅局 工作动态 | 1,304 | **0** |
| 文广旅局 通知公告 | 1,237 | **0** |
| 市政府 要闻/公告/首页 | 5,325 | 1 |

**这些栏目的文章是活动报道，不是活动预告。** 实测标题：

```
团队以楹联比武检验所学                      2026-10-13
"吉利姐"遇上大闸蟹，激活苏州金秋文旅消费新活力      2026-10-12
苏州博物馆原创话剧《光之棱镜——百年贝聿铭》圆满首演   2026-10-08
苏州博物馆第十九届"印象@苏博"画信活动颁奖仪式圆满落幕  2026-09-23
```

「圆满首演」「圆满落幕」「颁奖仪式」—— **是"发生了"，不是"将发生"。** 对一个判断未来需求的酒店收益系统，这些报道没有预测价值。

**结论：政府新闻栏目不是活动预告源。** 这不否定它们的价值，但它们的用途是核实（某活动确实举办过），不是发现。

### 再测真正的活动日历：visitsz

`tourism-visitsz-festival`（苏州市旅游咨询中心 节庆日历）已经注册并成功抓取。查看它的抓取深度：

| 项 | 值 |
| --- | ---: |
| 站点分页总数（页面自己写的「末页 page=663」） | **663 页** |
| 每页活动 | 12 条 |
| 页间重叠 | **0**（真分页） |
| 站点活动总量（估） | 约 7,956 条 |
| **已抓分页** | **1–12 页** |
| 已抓列表行 | 144 |
| 实际产出活动 | **39 条** |
| **覆盖率** | **12/663 = 1.8%** |

代码里写着这个限制是刻意的：

```python
# Verified horizon: pages 1-12 held the 92 not-yet-ended records of 144 scanned.
# The pager advertises 662 pages; that number is never followed.
page_cap = 12
```

```python
# crawler/run.py
MAX_ITEMS_CAP = 40
help="1-40 detail records per source; no pagination"
```

两个限制叠加：只读 12 页，且最多抓 40 条详情。**144 条列表行里有 104 条的详情页从未被请求。** 这不是提取失败，是根本没去抓。

## 二、未来活动在分页中的分布

扩页之前先测量：未来活动到底分布在哪些页。

| 页 | 行数 | 未来 | 有效率 | 发布日 |
| ---: | ---: | ---: | ---: | --- |
| 1 | 12 | 11 | **92%** | 2026-10-13 |
| 3 | 12 | 10 | **83%** | 2026-10-08 |
| 8 | 12 | 8 | 67% | 2026-09-29 |
| 12 | 12 | 6 | 50% | 2026-09-24 |
| 25 | 12 | 8 | 67% | 2026-09-18 |
| 35 | 12 | 5 | 42% | 2026-08-31 |
| **45** | 12 | **0** | **0%** | 2026-08-14 |
| 60 | 12 | 0 | 0% | 2026-06-30 |
| 100 | 12 | 0 | 0% | 2026-04-22 |

**规律：这个日历按发布时间倒序排列，越深的页是越早的发布，越早的发布对应越早的活动。** 未来活动的产率随深度衰减，到第 45 页（8 月中发布）归零。

**所以扩页的收益是有限的、有边界的** —— 前 35 页值得读，再深就是烧请求换历史内容。

## 三、改动

### 1. 自适应停止，而不是猜一个固定深度

```python
# crawler/sources/tourism/visitsz.py
page_cap = 40          # 硬上限
dry_page_limit = 6     # 连续 6 页没有未来活动就停
```

理由：固定深度必然错 —— 太浅漏掉未来的，太深读一堆历史。**改为"还在产出就继续，连续 6 页没产出就停"。**

`page_cap = 40` 的依据是实测分布：最深的真实未来活动簇在第 35 页，连续 6 页空档从第 39 页开始，所以限制 6 会停在第 44 页，不会切掉活跃内容。

### 2. 放开详情预算

```python
# crawler/run.py
MAX_ITEMS_CAP = 240    # 原为 40
```

新增 `--deep` 开关，一次把每个源的详情预算提到上限。

**只改深度不够：即使页码放开，`--max-items 40` 仍然只能发布 40 条。**

## 五、一个附带发现：微信内容其实已经在库里

visitsz 的详情页带有政府站自己标注的 **「原信息链接」**，指向 `mp.weixin.qq.com`：

```
来源：苏州第一丝厂微信号
时间：2026-10-16 - 2026-10-18
地点：苏州市南门路94号苏州第一丝厂入口处
活动简介 "百步芳草 四季书香" 2026'苏州阅读之夜系列活动 即将举办！
原信息链接： https://mp.weixin.qq.com/s/gsw7fQSFBRJv0sQRJqvBkQ
```

**「苏州发布」这类政府号的内容，政府站自己转载了，还留了原文链接。**

现有的 `visitsz` 适配器把这些链接**记录为来源凭据，但从不请求**（`WEIXIN_LINK` 只用于提取，代码注释写明 "recorded as provenance, never requested"）。

**这解决了"微信公众号内容抓不到"的问题，而且不需要碰验证码**：内容通过一个 robots 开放的政府站获得，微信链接只作为溯源留档。

## 六、记录的局限（不隐藏）

1. **可能漏掉孤立的未来活动簇。** 如果一个未来活动簇距离上一个超过 `dry_page_limit` 页，自适应停止会在它之前停。这是刻意的取舍：替代方案是读完 663 页去捞少量散件。

2. **站点总量约 7,956 条，本轮取 213 条。** 剩余的是历史活动（已结束），按「只取未来」的规则不采集。**随着时间推移，同样的抓取会自然覆盖新发布的未来活动** —— 每天定时任务是合适的机制，不需要一次性读完全部历史。

3. **visitsz 是 `OFFICIAL_GOVERNMENT` 信任等级，但它是转载方。** 标题和「来源」凭据来自场馆公众号，所以它的字段声明仍是 `Unverified`/`Needs Review`，**永远不会自动 Verified**。这一点没有因为抓取变多而改变。

4. **`venue-suzhou-arts` 和 `venue-suzhou-expo` 的状态在本轮之前已被其他人修好**（22→31、0→7），不是本轮改动带来的。

## 七、复现

```bash
# 本地
backend\.venv\Scripts\python.exe -m crawler.run --source visitsz --deep

# 生产（必须带环境变量，否则会写到默认路径）
sudo -u menduner env MENDUNER_DB_PATH=/srv/menduner/data/menduner.sqlite3 \
  ./venv/bin/python -X utf8 -m crawler.run --source visitsz --deep
```

**踩到的坑：手动运行不带 `MENDUNER_DB_PATH` 时，`database_path()` 返回 `/srv/menduner/backend/data/menduner.sqlite3`（一个空库），而 systemd 服务通过 `Environment=` 指向 `/srv/menduner/data/menduner.sqlite3`。** 第一次在服务器上运行就写错了库。已记录在案：手动运行任何采集都必须显式带上环境变量。
