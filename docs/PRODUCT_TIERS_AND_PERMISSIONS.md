# Menduner 分层与权限设计(2026-10-18)

> 这是**设计**,不是已完成的功能清单。文中"现在就有"指线上 `47.116.133.230` 已可用的能力,
> "NEW" 指还不存在、需要排期的新工作。所有数字来自线上数据集(2026-10-18,revision 22),
> 明细见 [`pilot-hotel-preview-20261018.json`](pilot-hotel-preview-20261018.json)。

## 0. 结论先行

1. **先卖"每周省多少时间",不卖"更多数据"。** 现有数据已经足够回答"未来一个月附近有哪些活动",
   问题不是缺数据,而是**太多且没排序**:苏州洲际酒店未来 30 天、5 km 内有 **91 场**活动,
   金鸡湖大酒店 91 场、沃姆酒店 95 场(≤10 km 最多 150+ 场)。销售经理要的是**从中挑出 5–8 场
   值得打电话的**,并知道**这周比上周变了什么**。这才是专业版的内容。
2. **不能卖"已核实"。** 线上 505 场活动里事件级状态是 493 条 Needs Review、12 条 Conflicting、
   **0 条 Verified**;且 90% 的活动来自第三方平台/社区(visitsz 260、cnena 149、场馆 50、
   豆瓣 27)。可以卖的是**可追溯**:每场活动都有来源链接(505/505)、每个字段有证据链
   (5,230 条)、冲突被单独标出。把"来源 + 冲突 + 字段证据"免费给看,是正确的;把
   "Verified" 做成付费卖点则是虚假承诺。
3. **套餐和权限必须分开设计**,你的判断是对的。建议三条轴:**套餐(能用什么服务)**、
   **岗位(能执行什么操作)**、**租户范围(能看哪部分私有数据)**;数据分三类:
   **公有共享 / 企业私有 / 平台内部**。当前系统只有第 1 条轴的雏形(公开数据),岗位和租户都还没有。
4. **企业版被租户隔离卡住,不是 UI 开关。** 现在只有一个 SQLite、一个共享库、没有任何私有数据;
   在接入酒店经营数据之前,必须先有 `tenant_id` 级的隔离与 API 作用域,否则"企业私有数据"只是口号。
5. **专业版建议先做"手工版"验证付费意愿**,再开发关注清单/导出界面:用系统每周给试点酒店
   手工做 4 期报告,看对方是否真的用、问什么、愿不愿意为此付钱。这比先写功能便宜得多。

## 1. 谁付钱、解决什么问题

**目标客户(第一批收窄)**:苏州单体酒店的**销售经理 / 市场经理 / 收益经理**。

**他们每周的真实任务**:下周到未来一个月的档期安排——附近有哪些展会、演唱会、赛事?
哪些和本酒店有关(距离、体量、日期)?信息可信吗?和上周比有什么变化?

**Menduner 交付**:以该酒店为中心的**一份清单**,每条带日期、距离、来源链接、证据状态、
变化标记;以及**一份可直接转发的周报**。

**省的时间**:目前销售要在抖音/大麦/公众号/场馆官网之间手工翻找、复制到 Excel、打电话确认
档期;Menduner 把"搜集"变成"审阅"。这是可量化的:**每周 2–3 小时 → 20 分钟**,而周报本身
可以直接进销售周会。

**不承诺**:收入预测。当前没有入住率、平均房价、间夜、预订进度这些结果数据(开放数据平台也
没有,见 [OPEN_DATA_FEASIBILITY.md](OPEN_DATA_FEASIBILITY.md)),所以"能准确预测收入"不能
作为付费承诺,只能作为后续研究。

## 2. 三个套餐(映射到现有能力)

| 能力 | 现在 | 免费版:了解城市 | 专业版:盯一家酒店 | 企业版:管多家酒店 |
|---|---|---|---|---|
| 活动浏览 / 地图 / 日历 / 活动清单 | ✅ 已有 | ✅ 全部 | ✅ | ✅ |
| **来源链接 + 字段证据 + 冲突标记** | ✅ 已有 | ✅ **必须免费可见** | ✅ | ✅ |
| 酒店周边筛选(半径/日期) | ✅ 已有(酒店活动情报) | ✅ 但不可保存 | ✅ | ✅ |
| 酒店组合对比 | ✅ 部分(多选组合) | ❌ | 1 家 | ✅ 多店 |
| 关注清单 / 保存视图 | ❌ NEW | ❌ | ✅ | ✅ |
| 变化提醒(新活动/改期/取消/状态变化) | ❌ NEW(需变化日志) | ❌ | ✅ | ✅ |
| 周报导出(PDF/Excel/链接) | ❌ NEW | ❌ | ✅ | ✅ |
| 团队 / 成员 / 岗位 | ❌ NEW(需用户表) | ❌ | ❌ | ✅ |
| 企业私有数据接入(经营数据/客户名单) | ❌ NEW(需租户隔离) | ❌ | ❌ | ✅ 约定范围 |
| 按约定范围提供 API | ❌ NEW | ❌ | ❌ | ✅ |

关于两个想法:

- **来源和核实状态免费可见** —— 完全同意,而且这正是与"爬虫聚合站"的差别:别人给你一堆标题,
  我们给你"这条来自哪里、哪个字段有冲突、原始链接是什么"。信任是免费的,工作流才是付费的。
- **专业版要形成闭环** —— 同意。**"选酒店 → 找相关活动 → 关注变化 → 出周报"**里,现有产品
  只完成了前两步;后两步(NEW)才是专业版的全部价值,也是为什么专业版不能只是"多几个图表"。
  另外,闭环意味着**相关性筛选**必须是产品的一部分:91 场活动不筛选,周报就没有可读性。

## 3. 三个权限维度与数据边界

### 3.1 维度分离(你的"付费等级 ≠ 数据权限"落地方式)

| 维度 | 决定什么 | 谁来配 | 示例 |
|---|---|---|---|
| **套餐(plan)** | 能使用哪些**服务** | 商业/合同 | 专业版可导出周报;免费版不可 |
| **岗位(role)** | 能执行哪些**操作** | 管理员 | 查看者只读;审核员可审核证据;平台管理员可管成员 |
| **租户范围(tenant)** | 能访问哪部分**私有数据** | 合同 + 管理员 | A 酒店成员只看到 A 的经营数据;看不到 B 的客户名单 |

三条轴**分别存储、分别校验**:套餐不写进用户表就完事,而是"功能开关";岗位不靠界面隐藏,
而是在后端端点校验;租户范围不是前端过滤,而是每个私有查询都带 `tenant_id`。

### 3.2 数据三类

| 数据类 | 内容 | 谁能看 | 现状 |
|---|---|---|---|
| **公有共享** | 城市活动、场馆、商圈、公开来源与证据 | 所有套餐;匿名可读 | ✅ 就是当前 `/api/dataset` |
| **企业私有** | 酒店经营数据(入住率/房价/间夜)、客户名单、内部备注 | 仅该租户成员 | ❌ 不存在(无表、无租户) |
| **平台内部** | 审核队列、场馆合并、错误日志、采集健康 | 仅平台岗位(审核员/管理员) | ⚠️ 有功能,但和客户页面混在一起 |

### 3.3 当前系统的真实状态(不能跳过的事实)

- 身份:**一个共享 basic-auth 登录**(`menduner`),昨天起后端会校验 `X-Menduner-Login`。
  **没有用户表、没有岗位、没有套餐字段、没有 tenant**。
- 写操作:**任何持有这个登录的人都能审核/合并/改坐标**;平台内部操作与客户功能没有分开。
- 私有数据:**零**。`hotels` 表是公开的酒店名录,不是某家酒店的经营数据。
- 因此:
  - **岗位**可以先做(小):`users(login, display_name, role, tenant_id)` + 端点校验;
  - **租户**是企业版的前置(中):私有表加 `tenant_id`,所有查询强制带作用域,默认拒绝;
  - **套餐**在试点期可以先"人工开通",不需要计费系统,但功能开关必须在**服务端**判断。

### 3.4 落到代码上的建议(与昨天的鉴权改动衔接)

```
nginx basic auth ──X-Menduner-Login──▶ backend/auth.py
                                        ├─ resolve_user(login) → role, tenant_id, plan
                                        ├─ require_role("reviewer") ── 审核/合并/坐标
                                        ├─ require_tenant()         ── 私有数据端点
                                        └─ require_entitlement("weekly_report") ── 套餐功能
```

- **默认拒绝**:公开数据集显式标注 public;其余端点必须命中角色或租户。
- **审核岗位必须独立**:`/review`、`/venues/merge`、`/venues/coordinates` 属于平台内部操作,
  客户账号(哪怕企业版管理员)也不应拥有。
- **内部工具与客户产品分离**:当前 `/evidence` 页面里混着审核按钮、场馆合并、前端错误日志
  (属于平台内部),应拆成"数据质量说明"(客户可读)与"审核台"(岗位可见)。这是开卖前
  必须做的一小步,否则客户能看到内部操作按钮。
- 套餐功能**只能服务端判定**:隐藏按钮不算权限。

## 4. 专业版的最小闭环与排期

### 4.1 闭环拆解(现状 → 缺口)

| 步骤 | 现状 | 缺口 | 新工作 |
|---|---|---|---|
| 1. 选酒店 | ✅ 酒店活动情报(酒店/组合/半径/日期) | — | — |
| 2. 找相关活动 | ✅ 距离筛选 | **相关性排序**(62/142 场是多日活动;**体量无数据**) | 规则:多日、类别(商务/体育优先)、场馆类型、来源等级;**不臆造规模** |
| 3. 关注变化 | ❌ | **变化日志**(新活动/改期/取消/场馆变化/状态变化) | 采集时写快照 → 逐次 diff;这是"每周都回来看"的理由 |
| 4. 出周报 | ❌ | 导出(链接/PDF/Excel)+ 口径说明 | 先做 Markdown/CSV,再做 PDF |

### 4.2 建议顺序(先验证付费,再写界面)

1. **P0(本周,小)**:拆"审核台"与客户页面;角色脚手架(查看者/审核员/管理员);
   记录每次写的身份(已有 `authenticated_as` + `reviewer`)。
2. **P1a(手工版 MVP)**:选 1 家试点酒店,**用系统手工出 4 期周报**(含相关性筛选与来源链接),
   每期问 3 个问题:用了吗?省了多少时间?少了什么?——**不写代码**。
3. **P1b(可卖的专业版)**:变化日志 + 关注清单 + 周报导出;先把"变化日志"做出来,
   因为它是订阅的续费理由。
4. **P2(企业版前置)**:用户表 + 套餐开关 + 租户隔离;之后再谈私有数据接入与 API。

### 4.3 验收标准(试点期)

- 周报**打开率/使用率**(对方是否在周会上用)、**从收到到反馈的时间**;
- **节省时间**由对方自评(每周省 X 小时)与"还会不会手工去别处找"两个指标判断;
- 不以"注册数/访问量"作为成功标准——这个阶段只有一两家客户。

## 5. 现在不建议做的

- **收入预测/ROI 估算**作为卖点:缺入住率、房价、间夜、预订进度,算不出来;继续作为研究。
- **按"能看更多数据"分层**:公开数据免费是信任基础;把数据本身锁起来会削弱付费理由。
- **企业私有数据接入**:在 `tenant_id` 隔离与审计完成前不接;酒店经营数据一旦进来就是
  责任边界,不能用"先跑起来"的方式处理。
- **计费系统**:试点期人工开通即可,先把"是否值得买"验证清楚。

## 6. 需要你确认的 5 件事

1. **第一家试点酒店**选哪家?数据上洲际/金鸡湖大酒店/沃姆酒店周边活动最多,但它们的需求
   可能偏展会/演出;如果目标是销售会奖(MICE),应优先选靠近博览中心/奥体中心的酒店。
2. **周报长什么样、怎么送**?PDF/Excel/邮件/在线链接;先手工发 4 期是否可行?
3. **专业版怎么定价**:按酒店/月、按坐席、还是按周报?试点期是否免费换反馈?
4. **企业私有数据先接哪一种**?(日入住率 / 平均房价 / 间夜 三者之一)——这决定租户模型
   要不要现在建。
5. **岗位先有几个人**:只有你一个人审核,还是会有第二个审核员?这决定角色是在配置里映射,
   还是要建正式用户表。
