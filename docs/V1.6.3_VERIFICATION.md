# V1.6.3 — evidence-based automatic verification + human review

## The rule change

V1.6.2 and earlier applied a blanket rule: **nothing** extracted from the web was ever marked
`Verified`. Every uncertain value was left for a human, which made the status vocabulary
meaningless (a date read from an official government page and a guessed category from a
community aggregator both ended up `Needs Review`) and made the map unreachable, because the
frontend only plots an event whose venue reference is `Verified`.

The rule is now narrower and evidence-based. A field claim may be auto-verified only when BOTH
hold:

1. **Authority** — the claim comes from an `OFFICIAL_GOVERNMENT` or `OFFICIAL_VENUE` registry
   source. Aggregators (commercial platforms, media, community/UGC) are never auto-verified, no
   matter how cleanly their pages parse, because the claim is theirs and not the organiser's.
2. **Determinism** — the value was read from an explicit machine field or an explicit labelled
   field, signalled by the codebase's own `explicit_*` / `official_*` method naming.

Everything else stays `Needs Review` / `Unverified` and is queued for a human on the Evidence
page. Non-claims are never auto-verified: a response URL is provenance, a reference id is
derived, and a category is a classification rule.

The rule is pure and live in `crawler/verification.py`, so it is tested exhaustively without a
database or network.

### Why the first implementation was wrong

The first version used a closed allow-list of method names. On real data it silently verified
nothing for dates because `explicit_leading_event_date` and `explicit_named_event_in_article`
had not been enumerated. The rule now keys off the naming convention the adapters already
follow, so a newly added explicit extractor is verified without editing the rule, while a
rule-based method can never slip through — `HEURISTIC_MARKER` is checked first, so a name like
`explicit_title_keyword_to_category_rule` is rejected.

### The venue-binding rule

A venue reference is a derived id, so under the field rule alone it can never be verified —
which is exactly why a venue's verified geography could never reach an itinerary. A second,
narrow rule closes that gap: a venue reference verifies when the venue **name** it points at is
itself verified **and** the reference was derived from that exact name. It joins two established
facts rather than asserting a new one. It is recorded under its own origin,
`auto:verified_venue_binding`, so it is never confused with the field-content rule.

## Human review

- Decisions live in their own table, `review_decisions`, **not** in the evidence rows. The
  pipeline deletes and re-inserts an event's field evidence on every crawl (the page may have
  changed), so a decision written into an evidence row would be destroyed by the next run. A
  decision is re-applied as an overlay every time evidence is rebuilt.
- A decision is bound to the **claim** it reviewed (`event_id + field + reviewed_value`), not
  merely to the field name. If a later crawl extracts a different value, the decision no longer
  matches and the field returns to the human queue: a reviewer must never be counted as having
  approved a value they never saw.
- API: `GET /review`, `GET /review/{event_id}`, `POST /review`, `DELETE /review/{event_id}/{field}`.
- UI: the existing Evidence & Data Quality page gained an action column (通过 / 驳回 / 修正 /
  撤回) and a mandatory reviewer name. A decision is attributable, and the page shows whether a
  verified value was decided automatically or by whom.

### Recorded decisions take effect immediately

`POST /review` rebuilds that one event's evidence rows through the pipeline's own projection,
reusing the registry's trust levels. Without it a reviewer would approve a field and see no
change until the next crawl, because the served rows are stored rather than computed.

## Bugs found and fixed while doing this

| Bug | Effect | Fix |
| --- | --- | --- |
| Human decisions keyed by the wrong field name | The API and UI store the frontend field name (`venueId`); the pipeline looked decisions up under the backend name (`venue_id`), so **every recorded decision was silently inapplicable** | The overlay is keyed by the field name the API and UI use |
| `decidedBy` set on every non-verified claim | Unverified fields were labelled `automatic`, implying a machine had decided them | `automatic` only when the rule actually verified the value; a pending claim has no decider, only an origin explaining why |
| `origin` was a bare `pending:human_review` for everything | The UI could not say whether a value awaited review because the publisher is an aggregator, because extraction was heuristic, or because the field is not decidable | The decision's origin is recorded for every outcome |
| Review decision not visible until the next crawl | Approving a field appeared to do nothing | The event is reprojected on `POST`/`DELETE /review` |
| Failed publish left half-written events | Events written before a mid-batch failure kept the failed source's id while their raw items said `Failed`, and their observations outlived the event rows | `withdraw_new_events()` removes events created by a failed attempt |
| `refresh_event` crashed on events with no observations | Legacy/demo rows are ingested by a different path; rebuilding them from an empty observation set destroyed their rows | Return early when there are no observations |
| Duplicate venue identity split the geography from the events | 苏州国际博览中心 existed twice: one row carrying the verified AMap place record, another carrying 40 exhibitions, so verified coordinates could never reach an event | Explicit, evidence-recorded mapping in `crawler/venue_aliases.json` + migration `scripts/canonicalize_venues.py` |

## Venue coordinates

45 venues used by events had no geometry. `scripts/enrich_venue_coordinates.py` queries the
AMap **Web service** and writes a coordinate only on an exact normalised name match in the
Suzhou prefecture, with the AMap place URL as provenance:

| Outcome | Count | Treatment |
| --- | ---: | --- |
| Exact name match in Suzhou | **20** | written as `Verified` GCJ-02 geometry with its `ditu.amap.com/place/...` source |
| Partial match only | 25 | **left without coordinates**, recorded with the candidate for a human |
| Lookup failure | 0 | — |

Partial matches are refused deliberately. The candidates include `李公堤文化创意街区停车场`
(parking) and `天平山景区-龙门一线天` (a rock formation, not the scenic area) — pinning an event
there would be wrong, and the project's rule is to leave the value absent rather than guess.
The 25 remain in the human queue.

A Web-service key is required and is **not** the JS key: the repository's `VITE_AMAP_KEY` is a
browser key and `AMAP_SECURITY_CODE` is a proxy signature. Both are rejected by
`restapi.amap.com` with `USERKEY_PLAT_NOMATCH` / `INVALID_USER_KEY`, and no signature scheme
works around a platform mismatch. Supply a key whose 服务平台 is set to **Web服务**, as
`AMAP_WEBSERVICE_KEY` in the environment or in `frontend/.env.local`.

## Batch confirmation of venue references

`scripts/confirm_venue_references.py` records ordinary review decisions in bulk for a reviewer
who has established a batch, so they need not click through hundreds of fields. It writes to
the same durable store as the Evidence page, requires an explicit `--venue` or
`--all-geocoded`, prints every event before writing, and supports `--dry-run`. It is never run
automatically by the crawler.

## Venue maintenance (V1.6.3 follow-up)

Two venue-centric views were added, both on the existing Evidence page and the map, with no
new route:

**Every event at one venue.** A theatre programmes many events, so clicking a venue lists them
all instead of opening one arbitrary event. The map's same-location popup now carries the venue
id and offers "查看该场馆全部活动"; the venue row in the field table offers the same. The list
shows date range, category, per-event verification status, and stays scoped to that venue.

**Duplicate resolution.** `crawler/venue_duplicates.py` PROPOSES pairs and never merges:

| Signal | Meaning |
| --- | --- |
| `exact` | identical after normalisation and region stripping |
| `containment` | one normalised name contains the other |
| `proximity` | both carry coordinates under 300 m apart |

Each candidate carries the events on each side, whether the canonical side has coordinates, and
any caveat — including the case where a row's "name" is really a whole address line, which is
reported rather than matched on its address text. The reviewer chooses the direction (both are
offered), and must give a reason; the decision is written to `venue_aliases.json` and to the
`venue_edits` audit table, and is revertible.

Detection deliberately surfaced a finding worth recording: **`苏州文化艺术中心`,
`苏州文化艺术中心大剧院` and `苏州文化艺术中心·金鸡湖音乐厅` are three different venues inside one
complex** (the complex, its grand theatre, its concert hall), so merging them would destroy
venue granularity. Likewise `苏州狮山大剧院` and `众戏剧文化艺术空间` sit 188 m apart but are
different venues. Only genuine full-name/shorthand pairs such as `苏州开明大戏院` / `开明大戏院`
should be merged, and the tool leaves that judgement to the reviewer.

**Coordinate entry.** The page takes longitude, latitude and a source URL per venue. The API
rejects a value outside the Suzhou bounding box, a non-`GCJ-02` system, and a missing or
non-HTTP source URL, then records the reviewer in `venue_edits`. Coordinates are therefore
always re-checkable, matching the AMap-provenance convention used by
`scripts/enrich_venue_coordinates.py`.

## Product fixes after the data cutover

### The dev launcher never started the frontend (root cause found)

`start.bat` failed with `Timed out waiting for http://localhost:5173/` and then killed both
service trees. The cause was not a slow build: it was an address that Vite never listens on.

`frontend/vite.config.ts` binds `127.0.0.1` (IPv4 only). Windows PowerShell 5.1 resolves
`localhost` to **`::1` first**, and the IPv6 connect stalls for about two seconds before it
falls back — while the probe used `-TimeoutSec 2`. That wait could therefore never see a 200,
however long the deadline was.

Proved by binding a throwaway server to `::1` only on port 5173 and probing with PS 5.1:

```
localhost    -> HTTP 200 in  125 ms
127.0.0.1    -> FAIL at     2014 ms
```

So `localhost` is IPv6-first here, which is exactly why an IPv4-bound Vite was unreachable
through it. The launcher now probes `127.0.0.1` (the address Vite prints) with 90/120/60 s
ceilings, while the URL it prints and opens stays `http://localhost:5173` because browsers fall
back and the AMap security-code origin must stay the documented local origin.

Two defects made this undiagnosable and are also fixed:

- **The service logs were empty.** PS 5.1 `Start-Transcript` does not capture native child
  output, so `.menduner-backend.log` held only a transcript header even while uvicorn was
  answering. Each service's real stdout/stderr is now streamed into its log (verified: the
  frontend log shows `VITE v7.3.7 ready in 373 ms`, the backend log shows
  `Application startup complete` and request lines).
- **A dead service hung the full window.** The worker now writes an exit marker and the probe
  fails fast quoting the last log lines, so a broken service reports its own cause instead of a
  generic timeout.

Measured: `start.bat` **exit 0 in 9.57 s** (previously exit 1 after ~42 s); killing the frontend
is detected in under a second. Cold vs warm Vite was 1.12 s vs 1.07 s, which is what ruled the
"slow build" hypothesis out.

## Evidence page: settling a whole event at once

A reviewer who has read one event's source page had to click ten times, and the flow made an
event impossible to finish: a field the page genuinely never states (an organiser it does not
name) stays `Missing` forever, and event-level status required every field to be settled.
Every event would therefore sit at 待复核 permanently.

**全部核查完毕** settles one event's factual fields in a single attributable action, and answers
with exactly what remains:

| Field kind | Treatment |
| --- | --- |
| Factual, has a value (`name`, `startDate`, `endDate`, `venueName`, `location`, `organizer`) | the reviewer confirms the value |
| Factual, no value | the reviewer confirms the **absence**, recorded under its own decision kind (`AbsentConfirmed`) with the note 人工确认：来源未给出该字段的值 |
| Conflicting | **never** bulk-approved; reported and left for individual resolution |
| Derived (`venueId`, `districtId`, `category`, `sourceUrl`, `city`) | **never** touched: no one can verify a reference id, a classification or a response URL by reading the page |

Recording an absence needed a new decision kind. Folding it into `APPROVE` with a null reviewed
value would have made the decision apply unconditionally, so a value extracted by a later crawl
would have been reported as human-verified — a reviewer credited with approving a value they
never saw. `ABSENT` applies only while the field is still empty.

**Event-level status now ignores derived fields.** Counting them made 已核验 unreachable: a
`category` claim is a classification rule's output and a `sourceUrl` is provenance, so events
could never reach the state however carefully every fact was checked. The badge is now scoped to
what it can honestly mean — all factual fields verified — while the derived fields keep showing
their own status in the table. On the production database this took one reviewed event from
`Needs Review` to **`Verified`**.

## Hotel demand radius on the map

The 酒店活动情报 radius slider (1–30 km) now draws the corresponding circle on the map, centred
on the selected hotel. This is the one boundary the product can honestly draw: it is the filter
the page already applies, made visible, and every coordinate behind it is a verified GCJ-02
position. The caption says it is a straight-line radius and **not** a travel-time isochrone, and
the page's own warning that proximity is not proof of demand still stands.

A district-boundary overlay was considered and rejected: meaningful 商圈 polygons for Suzhou are
not available from a verifiable source, and drawing an unverifiable boundary would claim
knowledge the data does not support.
