### Safety incident: the public-page redirect check was disabled by default

The shared fail-closed base class for Damai, Huodongjia, Douban and CNENA was changed to:

```python
def public_page(self, url, allowed_redirect=None):
    ...
    page = self.client.get(url, allowed_redirect=allowed_redirect) if allowed_redirect \
        else self.client.get(url)          # <-- no restriction at all
```

Calling `public_page(url)` without an argument — which every existing adapter does — passed
`allowed_redirect=None` and therefore **skipped the redirect check entirely**. Measured effect:
a Damai detail page redirecting to `/login` was followed and fetched (HTTP 200) and only failed
later with a confusing `KeyError: 'id'`. The pre-existing test
`test_v16_priority.py::test_detail_redirect_to_login_is_rejected_without_target_request` caught it.

Restored to fail closed:

```python
if allowed_redirect is None:
    allowed_redirect = self.is_public_url
```

Verified: the `/login` redirect is rejected with *"Redirect leaves approved public page routes;
no target request made"*, `/login` is never requested, and all four adapters still work live
(douban 8 pages / 5 events / 55 evidence; huodongjia 2 / 1 / 11; cnena 6 / 5 / 50).

Two regression tests were added so neither direction can drift again:
`test_public_page_omitting_allowed_redirect_still_enforces_approved_routes` and
`test_public_page_still_allows_a_redirect_within_the_approved_routes`.

**Lesson for the next phase:** `public_access.py`, `http.py`, `run.py`, `registry.py` and
`source_registry.yaml` are shared, security-relevant files. A change that makes one adapter's
test pass can silently remove a protection for four other sources. These must stay single-owner,
and the owner must run the *whole* suite, not just the adapter's own tests.

Test suite after the fixes: **99 passed** under the default (GBK) Windows locale.

## Open gaps found while landing

### 0. BLOCKING: the Event Map cannot plot any real event (two independent reasons)This is the most serious finding of V1.6.2 and it is structural, not cosmetic.

`frontend/src/utils/data.ts::eventCoordinates()` returns `null` for a non-demo event unless
there is **a `venueId` evidence row whose status is exactly `Verified`**:

```ts
if (!event.demo && ( /* Conflicting|Needs Review */ || !data.evidence.some(
      (e) => e.entityId === event.id && e.field === "venueId" &&
             e.value === event.venueId && effectiveStatus(e) === "Verified" ))) return null;
```

Measured on the production database:
- `crawler_evidence.venue_id`: **11 `Needs Review` + 1 `Missing`, 0 `Verified`**.
- The same statuses appear in the frontend-facing `evidence` table for `field='venueId'`.

Because the project's core rule is that nothing is ever auto-verified, a crawled `venueId` can
never be `Verified`. So the condition can never be satisfied and **every real event is excluded
from the map regardless of coordinates**. This is why the map appeared to work during the demo
era: the mock events carried `demo: true`, which short-circuits the check.

Second, independent reason: only 2 of 10 venues have `coordinates`, and **no event references
either of them** (`v-expo` and `v-theatre` have 0 events each). The 8 venues the real events do
use (苏州文化艺术中心·金鸡湖音乐厅, 苏州奥体中心体育场, 李公堤文化创意街区, 金鸡湖景区,
阳澄湖旅游集散中心, 苏州狮山大剧院, …) have `coordinates: null`.

Consequence: the City Event Map is blank; `frontend/src/components/Map/index.tsx` skips every
event whose venue lacks coordinates and renders **no empty state**, so it looks broken rather
than explicitly empty.

This needs a product decision, and it should not be "just make it Verified" — that would break
the project's central integrity rule. Legitimate options: (a) treat a venue's *location identity*
as a separately verifiable entity-level fact (the legacy AMap POI rows already do exactly this via
`ditu.amap.com/place/...` source URLs) and let the map plot on verified venue geography while the
event→venue *claim* stays `Needs Review`; and/or (b) add an explicit "此活动场馆缺少已核验坐标" empty
state. **Not changed in V1.6.2 — needs the user's decision.**

### 1. Event Map coordinate gap (see 0)
No real event venue has `coordinates` (8 of 10 do not), and by design "no verified evidence means
no map pin" (V1.5 principle). `frontend/src/components/Map/index.tsx` skips every event whose venue
lacks coordinates (`if (!c || !venue) continue`) and shows no empty state, so the page looks broken
rather than explicitly empty. This is the second half of finding 0. Options: add verified AMap POI
coordinates per real venue with provenance (the same pattern the legacy `v-expo`/`h-inter` rows
already use), and/or add an explicit empty state. **Not changed in V1.6.2 — needs a decision.**

### 2. District Insights has no data
`districts` is now empty because the only district rows were demo placeholders (金鸡湖商圈,
独墅湖商圈) and were archived. `districts=[]` is valid for the API, but the District Insights
page has nothing to show. Needs either a verified district taxonomy or an explicit empty state.

### 3. Hotel Intelligence has one hotel
Only 苏州洲际酒店 (real AMap POI) remains; the second row was a DEMO placeholder. The demand
analysis needs a hotel set with coordinates to be meaningful.

### 4. Future-event coverage is thin
Of 12 real events only **4 start on/after 2026-10-13**; the rest are historical observations
(July–October). The frontend default window (year=2026, month=10) shows 4 events of which three
are already past. Increasing *future* coverage is the real V1.6.2 objective and depends on the
recon results.

### 5. Shared-registry write-back race
`crawler/coverage.py::source_coverage()` rewrites `crawl_status`/`reason`/`last_checked` into
whatever registry path it is handed, and `attach_coverage()` defaults to the real
`crawler/source_registry.yaml`. Every CLI crawl therefore mutates the tracked registry. This is
intended for the CLI but makes the registry a shared mutable file during parallel work, and any
test that reaches `attach_coverage` would corrupt it. Tests must not call it.
