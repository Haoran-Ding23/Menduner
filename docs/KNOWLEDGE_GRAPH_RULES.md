# 知识图谱:按规则自动生成(2026-10-16)

知识图谱现在连接五类东西:**活动地点、周边酒店、餐饮商户、交通条件、目标客群**。

**它不是一个活动一个活动写出来的。** 图谱由规则从数据生成:选中任意一个活动,规则读该活动自己的字段、它场馆的核验坐标、以及场馆周边的记录,当场算出节点和边。第 456 个活动和第 1 个活动走的是同一段代码,新采集到的活动不需要改图谱代码就出现在图里。

---

## 一、三类规则,边上有标识

每条边都带 `rule`(规则 id)和 `reason`(为什么这条边成立),点开线就能看到。

| 规则族 | 依据 | 图上画法 | 规则 id |
|---|---|---|---|
| **来源** | 来源记录本身:活动的场馆引用、场馆的商圈、AMap 地点记录 | 实线 | `held_at`、`located_in` |
| **距离** | 双方核验坐标算出的直线距离(坐标是记录,距离是算术) | 实线,标 `x.xx km` | `near_hotel`、`near_restaurant`、`near_transit` |
| **规则假设** | 由活动字段推导的判断,不是来源声明 | **虚线**,标「规则假设」 | `audience_*`、`audience_hotel_tier`、`related_event` |

页面底部有一块「本图由 N 条规则自动生成」,逐条列出本次触发的规则、触发依据和它生成了几条关系。

## 二、目标客群怎么判断出来

客群由活动自身的字段推导,**只在该字段真的存在时才触发**,并且每条规则都写明触发条件:

| 规则 | 客群 | 触发条件 |
|---|---|---|
| `audience_business` | 商务差旅客群 | `category = business` |
| `audience_culture` | 文化消费客群 | `category = culture` |
| `audience_sports` | 体育观赛客群 | `category = sports` |
| `audience_education` | 教育家庭客群 | `category = education` |
| `audience_folk` | 民俗节庆客群 | `category = folk` |
| `audience_government` | 公共事务客群 | `category = government` |
| `audience_others` | 综合消费客群 | 类别未归类时的兜底(类别规则命中时不触发) |
| `audience_multi_day` | 多日住宿需求 | `startDate → endDate` 跨度 ≥ 2 天 |
| `audience_large_scale` | 大规模聚集 | 已记录的 `attendance ≥ 5000` |

客群节点是**共享节点**:多个活动会连到同一个「商务差旅客群」上,所以这张图不只是单活动的邻域,客群这一层是可以跨活动聚合的。

客群还会连到图中已有的酒店,层级偏好写成显式假设表(`TIER_HYPOTHESES`):商务差旅 → 高端/中端,文化消费 → 中端/舒适,等等。**这是假设,不是结论** —— 虚线、标「规则假设」、可整层关掉。它存在的理由是:客群节点如果不连到供给侧,就只是一个悬空的标签。

## 三、餐饮与交通:高德真实 POI

数据落在新的 `places` 表(和 hotels 同级),由 `scripts/enrich_places.py` 采样:

| 类型 | 高德类型码 | 采样半径 | 每个场馆保留 |
|---|---|---|---|
| 餐饮 | `050000` | 1500 m | 最近 6 家 |
| 地铁站 | `150500` | 2000 m | 最近 3 个 |
| 轻轨站 | `150600` | 2000 m | 最近 2 个 |
| 公交车站 | `150700` | 1000 m | 最近 3 个 |
| 火车站 | `150200` | 12000 m | 最近 2 个 |
| 长途汽车站 | `150400` | 12000 m | 最近 2 个 |
| 机场 | `150100` | 30000 m | 1 个 |

图上绘制的半径与采样半径一致(`TRANSIT_REACH_KM`),所以「地铁 2.5 km / 公交 1 km / 火车站 12 km / 机场 30 km」是同一套口径。

**分类只认来源自己声明的类型串**(`crawler/places.py`),不靠名字猜:餐饮保留高德的中类(中餐厅/咖啡厅/快餐厅/餐饮相关场所…),交通只保留设施本身,并显式丢掉:

- 地铁站的「出入口」、火车站的「站台/售票/候车室/进站口」——**站的一部分不是站**,问「怎么到这里」不该答「3 号口」;
- 停车场(25 个交通 POI 里 11 个是停车场);
- 港口码头(金鸡湖的游船码头是旅游,不是到达方式);
- 直升机场与医院停机坪(不是旅客交通)。

每行都留 `sourceUrl`(高德 `ditu.amap.com/place/<id>`)、`declaredType` 原文、采样场馆 `sampledNearVenueId`、采样半径 `sampledRadiusM` 和到场馆的距离。

**覆盖边界**:这是「有活动、且有核验坐标的场馆周边」的采样,不是全城 POI 库。本轮 88 个场馆 → 793 条地点(餐饮 431、交通 362)。

## 四、怎么重新生成

```powershell
# 采样(需要 AMAP_WEBSERVICE_KEY;dry-run 默认)
.\backend\.venv\Scripts\python.exe -X utf8 scripts\enrich_places.py --db <库> --apply

# 把采样结果搬进另一个库(只写 places 表,幂等)
.\backend\.venv\Scripts\python.exe -X utf8 scripts\import_places.py places.json --db <目标库> --apply
```

采样与导入分开,是因为密钥只在本地、而权威场馆坐标在部署环境:采样在本地做,再把这 793 行搬过去,不必复制 160 MB 数据库,也不必把密钥放到服务器上。

## 五、测试与线上验证

- 后端 6 项(`crawler/tests/test_places.py`):分类规则(含出入口/停车场/码头/直升机场被拒)、表是增量幂等、`/places` 与 `/dataset` 投影、采样出处字段。
- 前端 23 项(`frontend/tests/knowledge-graph.test.ts`):**每个节点和每条边都必须带 rule 与 reason**;同字段不同名字的两个活动必须生成同构的图(证明没有写死);七种类别各自映射到唯一客群;多日/大规模规则只在字段存在时触发;餐饮 1.5 km、公交 1 km、地铁 2.5 km、火车 12 km、机场 30 km 的边界;无坐标的地点不画;层级假设只连「图中已有的酒店」且只连规则允许的层级;规则开关关掉后整层消失。
- 合计:后端 525 通过,前端 122 通过。

线上(47.116.133.230):`/api/status` → 456 活动、14 来源;`/api/places` → 793 行;`/api/dataset` 含 `places`;前端 release 已替换并核对过 nginx 实际返回的 chunk 与本机构建字节一致(SHA256)。部署时保留了库里的 137 条人工审核决定与 73 条场馆修改。

## 六、没有声称的东西

- 客群是**规则推导**,不是来源声明,更不是统计结论 —— 图上虚线,不构成证据。
- 客群到酒店层级的边是**假设**,不能当成「这批客人一定住哪一档」。
- 餐饮/交通是**采样**,馆场周边之外的商户不在库里;`sampledNearVenueId` 与半径让这个边界可查。
- 人数、房量这类需求侧数字仍然缺(见 `HOTEL_INTERVIEW_20261015.md`),图谱不会用客群标签去暗示它们存在。
