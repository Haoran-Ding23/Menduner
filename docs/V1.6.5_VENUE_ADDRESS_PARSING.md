# V1.6.5 — venue addresses are the address part of the source's place line

**Date:** 2026-10-15 (Asia/Shanghai). **Trigger:** the coordinate-maintenance screen showed
场地 rows whose "address" was the source's whole place line — the clearest case being

```
山丘livehouse-斜塘店   1 个活动 · 苏州 吴中区 山丘livehouse-斜塘店 松涛街1088号斜塘老街36幢
```

The claim was never wrong; it was simply not an address. `松涛街1088号斜塘老街36幢` is the
address inside it, and `松涛街1088号` is the form a map lookup should start from.

**Scope:** how a venue row's `address` is derived, and the one place it is used for lookup. The
event's `location` field is untouched: it stays the source's own string, with its own snippet and
evidence (`crawler_evidence.field_name = 'location'`).

---

## 1. Two shapes reach the venue row

| Source | Place line as published | What the row used to store |
| --- | --- | --- |
| 豆瓣同城 (community) | `苏州 吴中区 山丘livehouse-斜塘店 松涛街1088号斜塘老街36幢` | the whole line |
| visitsz (tourism) | `苏州市吴中区东苑路1号苏州保利大剧院大剧场` | the whole line |

Both encode the same three things: an administrative prefix (city / district), a repetition of the
venue's own name, and the address. Only the third belongs in an address field, which is what a
human reads while entering coordinates and what `scripts/resolve_venues_by_address.py` sends to
AMap.

## 2. The rules (`crawler/addresses.py`)

Deterministic, no model, no guessing — `street_address(place, venue_name=…)`:

1. Leading words that are a city (苏州/苏州市/昆山/常熟/太仓/张家港), a district/county/镇/新区, or
   the venue's own name are dropped. This works per token for a spaced place line and per
   character-run for a run-on one (`太仓市半泾南路3号…` -> `半泾南路3号…`).
2. The address starts at the road that carries the string's house number; everything before it is
   administrative text or the repeated name.
3. A repetition of the venue's name after the address is cut, including a city word written with
   it (`观前街北局11号|苏州|开明大戏院大剧场` -> `观前街北局11号`).
4. The result must still contain that road and house number. **A string with no house number yields
   `None`** — a scenic area, a bare venue name or a metro station is never turned into an address.

`lookup_address(place)` reduces the same line further, to road plus house number, which is the
discriminating form for a map query (`松涛街1088号`).

## 4. How it is applied

* **New rows** get the derived address at crawl time — `crawler/pipeline/__init__.py` calls
  `venue_address(location, venue)` instead of taking the whole `location` whenever it contains 号.
* **Existing rows** were brought in line by `scripts/normalize_venue_addresses.py` (dry-run by
  default, `--apply` to write, `--report` for the audit trail). It only rewrites a row whose stored
  address is *exactly* one of the `location` claims recorded for that row's own events, so a value
  that came from anywhere else — the alias file's canonical rows, the curated coordinates list — is
  never overwritten. 32 rows were rewritten and the script also filled the arts-centre row, which
  had no address at all.
* **Lookup** tries the full street address first and falls back to the reduced road+number form:
  `scripts/resolve_venues_by_address.py` now reports which query matched (`address` / `road+number`).

## 6. Tests

`crawler/tests/test_addresses.py` (8 checks) pins every rule on the live strings, including the
reported case, the dangling-city trim, the detail-preserving cases (`平江街道皮市街9-69号(开元里2楼)`),
the no-house-number refusals, and one end-to-end pipeline check that the event's `location` claim is
still stored verbatim while the venue row gets the derived address. `pytest crawler/tests
backend/tests` -> **474 passed**.
