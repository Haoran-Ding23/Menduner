# 套餐与升级(客户侧,2026-10-18)

**定位**:这是给**客户**看的付费面,不是内部规划文档。它回答"我为什么花钱、花钱能多用什么"。
内部规划面板已删除;本页替代它,并已接入产品导航。

- 页面:`/plans`,导航项「套餐与升级」,对**所有访客**可见(客户要能先看到能解锁什么)。
- 两条承诺:
  1. **公开城市数据永久免费**——活动、来源链接、字段证据、数据质量在所有套餐里完整保留;
  2. **付费买的是工作流**——围绕某家酒店的筛选、区域对比、周报与变化提醒、多店管理,
     而不是把公共信息锁起来。

## 三档套餐

| 套餐 | 价格 | 面向 | 已上线能力 |
|---|---|---|---|
| 免费版 | ¥0 | 先了解这座城市 | 活动地图 / 日历 / 清单 / 场馆清单 / 知识图谱 / 数据质量与来源 |
| 专业版 | ¥980 / 酒店 / 月(试点四期免费) | 盯住一家酒店 | 酒店活动情报(单店周边筛选)、商圈洞察;周报导出与变化提醒即将上线 |
| 企业版 | ¥780 / 酒店 / 月(多店) | 管理多家酒店 | 专业版全部 + 多酒店组合对比;团队权限即将上线;私有数据与 API 后续 |

价格与试点承诺与 `PRODUCT_TIERS_AND_PERMISSIONS.md` 保持一致。企业版单价更低是因为按酒店数
打包(多店折扣),不是功能更少。

## 锁定与开通在产品里怎么体现

1. **导航**:「酒店活动情报」「商圈洞察」始终可见;套餐不够时带 🔒 图标,提示"需要专业版"。
   可见是为了让客户知道有什么,锁只是为了说明它属于哪一档。
2. **功能页**:直接访问被锁页面时,显示说明卡(属于哪一档、为什么付费、公开数据仍免费):
   未登录 → 「用邀请码注册试用」+「已有账号登录」;已登录但无有效付费期 → 「查看套餐并申请开通」。
3. **开通链路(真实)**:邀请码注册 `/register` → 四周试用(状态「试用中」)→ `/plans`
   提交开通申请 → 对公转账 → 管理员在审核台确认收款 → 账户变为「已开通」,导航锁图标消失,
   酒店情报解锁(专业版限**一家**酒店,企业版出现「酒店组合」多选与批量按钮)。
4. **到期**:订阅到期后服务端把套餐回落到免费版,锁图标回来,客户可再次申请续费。

## 开通流程与边界(必须说清楚)

- **没有在线支付**:正式服务走对公转账,金额按 专业版 ¥980/酒店/月、企业版 ¥780/酒店/月
  计算,以合同为准;产品只记录"申请"和"运营确认",不会假装收到钱。
- **套餐由服务端判定**:`backend/accounts.py` 每次请求按试用/订阅日期推导有效套餐;过期账户
  即使数据库里还写着 `pro`,也只会拿到免费版能力。前端只根据服务端返回的套餐展示。
- **邀请制**:没有邀请码不能注册;邀请码由管理员在审核台生成,可设套餐、试用天数、可用次数与
  过期时间,用完/过期即失效。
- **完整操作与安全说明**见 [ACCOUNTS_AND_ACTIVATION.md](ACCOUNTS_AND_ACTIVATION.md)
  (含 TLS/限流/找回密码等上线前待补项)。

## 安全与信任注意

- 付费墙**不锁公开数据**:任何套餐都能看活动、来源与证据;这既是承诺,也是差异化。
- 套餐由客户账户决定,账户由邀请码开通、由运营确认对公转账后生效;前端只做展示。
- 给客户演示时不要把它描述为"已收费/已开通",除非订单确实已确认(状态显示「已开通」)。

```bash
curl -o /dev/null -w '%{http_code}\n' http://127.0.0.1/plans     # 200(SPA)
curl -o /dev/null -w '%{http_code}\n' http://127.0.0.1/api/dataset  # 200(公开数据仍免费)
curl -s http://127.0.0.1/api/account                                # 匿名:authenticated=false
```

浏览器:导航「套餐与升级」→ 三档与能力对照 → 「用邀请码注册」→ 注册后显示「试用中」,
酒店活动情报解锁(专业版=单店);试用结束/未开通账号看到「申请开通」。
